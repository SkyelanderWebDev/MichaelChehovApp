## Scope shipped in this build

1. **Schema follow-up** (`supabase/migrations/20260703170000_connect_chat_invitations.sql`, additive; depends on the 0.2.0 chat migration):
   - `chat_rooms.kind` now allows `leadership` (constraint swap; framed in UI as a private beta coordination/leadership *group room*, explicitly not a DM).
   - `chat_room_invitations` — owner-only email invitations: `id, room_id, invited_email, invited_email_normalized, invited_by, token_hash (unique), status pending/accepted/revoked/expired, expires_at, accepted_at, accepted_user_id, created_at`.
   - **Token hygiene:** the raw token exists only in the `create_chat_room_invitation` RPC return (shown once to the owner). Only a SHA-256 hex hash is stored; `token_hash` (plus `invited_email_normalized`, `invited_by`, `accepted_user_id`) carries **no client select grant**, so no client can read hashes even for their own rows.
   - `create_chat_room_invitation(target_room, invitee_email)` — SECURITY DEFINER, owner-of-open-room only, validates email, caps live pending invites at 50/room, supersedes (revokes) a prior pending invite for the same room+email (unique partial index enforces one live invite per room+email), 7-day expiry.
   - `accept_chat_room_invitation(token)` — SECURITY DEFINER, single-use, requires signed-in caller, pending + unexpired invite, caller `auth.users.email` matching `invited_email_normalized`, open room; inserts membership and marks the invite accepted. Expiry is enforced at accept and derived at read (an update-then-raise status flip would roll back with the exception — caught by the local smoke and fixed).
   - `revoke_chat_room_invitation(invitation)` — SECURITY DEFINER, owner-only, pending-only.
   - RLS: invitation rows are selectable **only by the room owner** (column-scoped grant), so members/outsiders cannot harvest invitee emails. All writes go through the definer RPCs; there are no client insert/update/delete grants.
   - No service-role anywhere in the client. All definer functions use `set search_path = ''` with EXECUTE revoked from public/anon.
2. **UI**:
   - `ChatRoomsPage`: create form gains a `Leadership` kind with copy "private group room for beta coordination and leadership … still a group room rather than a direct message"; non-creators now see an explicit "Room creation is limited to approved beta hosts." panel instead of nothing; signed-in visitors with a parked invite token are routed to finish the accept.
   - `ChatRoomPage`: member count in the header meta; owner-only **Room admin** panel with an email-invite form, one-time invite-link display + copy button, and a sent-invites list (status pills incl. derived expiry, revoke for pending). Honest copy: *"This build doesn't send email yet — copy this link and send it to <email> yourself."* No fake delivery.
   - New `/connect/chat/invite?token=…` route (`ChatInvitePage`): signed-out visitors get the tester-access gate and the token is parked in localStorage; after sign-in the accept runs automatically and routes to the room. Wrong-email/expired/revoked/used/closed-room tokens show clear errors and grant no membership.
3. **Store** (`chatStore.ts`): `createInvitation`, `listRoomInvitations`, `revokeInvitation`, `acceptInvitation`, `inviteLink`, `invitationDisplayStatus`, and pending-token park/read/clear helpers.

## Email delivery status (NOT wired — by design this sprint)

There is no email provider in this stack (no server-side send path; service-role must never ship to the browser). This build implements the full DB/client invitation groundwork and an owner copy-link handoff, and does **not** fake delivery. To send real invite emails, Dawson must choose and provision ONE of:

- **Supabase Edge Function + transactional provider** (e.g. Resend/Postmark): needs provider account + API key as a Supabase function secret, a verified sender domain, and an edge function that owner-authenticated clients call; or
- **Supabase Auth admin invite** (`auth.admin.inviteUserByEmail`) via an edge function: needs hosted SMTP config on the Supabase project and ties invite emails to auth signup flow.

Either lane is server-side only and needs Dawson approval (provider spend/accounts). Local Mailpit exists in the local stack but only captures Supabase Auth emails; it cannot stand in for a production provider.
